# Aegisub 协作版 — 需求与技术共识文档

> 本文档整理自前期设计讨论与代码基线审查，仅收录已达成共识的内容。
> 用途：作为 Aegisub Together v1 的需求、协议与实现基准。

---

## 1. 背景与动机(为什么做)

- 字幕组使用 Aegisub 制作 .ass 字幕,现有多人协作方式是**把视频分段交给多个人分头做,最后手动合并**。
- 分段交付的痛点:没有单一可信的主文件、合并/衔接麻烦、样式不统一、校对意见靠群里贴时间码来回喊、组长看不到整体进度。
- **核心场景是"激光烤肉"(极速出片)**:时轴、翻译、校对三个工种在**同一份字幕文件上同时开工**,流水线并行以缩短出片时间。三人绝大多数时候工作在不同的行上,行级锁 + 快速释放足以支撑并行。

## 2. 范围决策(已明确)

### 做
- 在 **Aegisub 现有 C++ 桌面程序基础上开发**(fork),做成 **C/S 架构**。
- **只同步核心 .ass 字幕数据**：Dialogue、Styles、Script Info 与协作所需 Extradata。不同步视频、字体/图片附件和 Aegisub Project Garbage；视频及附件由各成员本地自备。
- **不连接服务器时,行为与原版 Aegisub 完全一致**(离线即单机)。用 feature flag 包住全部协作代码:未配置服务器地址 = 纯单机。
- **并发控制采用行级硬锁**:基于活动行(焦点),有人焦点在某行时,他人不得编辑该行。锁为**房间级可开关策略**(见 §6)。

### 明确不做(已否决的方案)
- ❌ 不做 Web 编辑器 / 不重写为网页应用。
- ❌ 不做视频同步 / 代理视频流 / 服务端转码。
- ❌ 不用 CRDT / OT(有服务器定序 + 行级锁,不需要)。
- ❌ 不做字段组锁、不做字段级自动合并、不做三方合并 UI(均因复杂度否决;并发控制统一为行级锁)。
- ❌ 行内(文本内部)实时协同编辑不做。同步最小单元为行的字段。
- ❌ 不做纯 Lua 的 Pull/Push 原型阶段(MVP-0 已取消),直接开发产品;后端验证由 M1 的协议级自动化测试承担(见 §12)。

### 基线选择
- fork 严格基于提交 **`8165f1ad5ec8b5f3c56e0c3b19b8126f581abd58`**，开发分支为 `feat/collaboration`；不得混入该提交之后的上游改动。
- 协作代码尽量收口在少数模块(extradata 发号、commit 钩子、网络子系统、网格锁/presence 绘制),便于后续跟上游 rebase。
- v1 协作客户端只承诺 Windows；Linux/macOS 必须继续编译并保持原版离线行为，协作模块在这些平台关闭。

## 3. 用户故事(均发生在同一份实时同步的文件上)

- 作为**时轴**,我切轴/打空轴后,新行立刻出现在翻译和校对的网格里,无需导出交付。
- 作为**翻译**,我焦点所在的行被我锁定,他人无法同时修改,我不会被覆盖;我切走焦点的瞬间锁即释放。
- 作为**校对**,我看到某行显示"翻译君正在编辑"且为只读时,可以等待几秒或通过批注旁路留下修改意见。
- 作为**任意成员**,我能在网格中看到每一行的锁定状态与占用者名字;被他人锁定的行我仍可**选中查看**(浏览永不被阻止),只是不能编辑。
- 作为**要跑批处理脚本的成员**,我开启"维护模式"后获得全文件独占写权限,其他人临时只读,跑完释放。
- 作为**断线重连的成员**,若我离线期间修改的行也被他人改过,系统逐行让我二选(保留服务器版 / 用我的覆盖),不静默丢弃任何一方。

## 4. 数据模型

### 4.1 行稳定 ID(collab_id)
- 每行 dialogue 挂一个稳定 ID,**存储在 Aegisub 的 extradata 中**,key 为 `collab_id`。
- ID 格式:**持久化的 50-bit Base32 客户端前缀 + 自增计数**(例:`9K3MT7Q2CD-128`),不用完整 UUID。前缀和计数保存在本机配置中。
- ID 使用 `_aegi_collab_id` extradata key；位置键使用 `_aegi_collab_pos`。
- 生成时机:commit 钩子中,扫描到无 `collab_id` 的行即铸号。
- 行 ID 是锁定/同步/批注/版本追踪的统一主键。**这是整个系统的地基,最先实现。**

### 4.2 行顺序:服务端分配的分数索引
- 不用数组索引标识顺序。insert/move 携带 `left_id`/`right_id` 锚点，由服务器按当前权威顺序分配 Base62 字符串位置键。
- 两个锚点仍有效且顺序正确时放在二者之间；仅一个有效时放在其相邻侧；均失效时放到文档末尾。并发插入由服务器处理顺序决定。
- 客户端按位置键渲染；普通插入不改动其他行的位置键。
- 任一位置键超过 64 字符时，服务器在一个原子 `reindex` 屏障中重排所有位置键；行 ID 与可见顺序不变，客户端清空在途顺序假设后继续。

### 4.3 行版本号
- 每行带版本号,每次针对该行的 commit 递增。客户端提交 op 时携带"我基于的版本号"。
- 用途:①锁关闭模式下的冲突检测(§6.5);②断线重连时识别"双方都改过的行"(§12 M3)。锁开启且在线时,锁本身已保证单写者,版本号仅作一致性校验。

## 5. 同步引擎

### 5.1 Op 模型
基本 op(以行 collab_id 为主键):
- `modify(line_id, fields, base_version)` — 修改字段
- `insert(line_id, left_id, right_id, data)` — 插入行，由服务器分配位置键
- `delete(line_id, base_version)` — 删除行(服务器侧保留墓碑)
- `move(line_id, left_id, right_id, base_version)` — 移动行

补充:
- `restore(line_id)` — 复活被删除的行(用于撤销删除,恢复墓碑及其上挂载的批注/历史)。
- `replace_styles(styles, base_version)` — 原子替换 Styles 节。
- `replace_script_info(entries, base_version)` — 原子替换 Script Info 节。

### 5.2 服务器定序
- **服务器是唯一定序权威**：每个成功原子批次递增一次单调 `room_revision`，批内 op 按数组顺序执行并共享 revision。
- 客户端严格按 room revision 应用广播；重复 revision 幂等忽略，发现缺口立即请求快照。
- 新客户端入房时先收**全量快照 + 当前 revision**，之后只收增量。

### 5.3 确认态与投影态 — 客户端侧
- `confirmed shadow` 只保存服务器已经确认的权威状态，绝不在本地发送时提前推进。
- `pending batches` 按 WebSocket 发送顺序保存所有未确认本地批次；`projected shadow = confirmed shadow + pending batches`。
- 本地 commit 时以当前文档对 projected shadow 做 diff，形成下一批次。服务器回给发送者的规范化广播（含 ID/位置键映射）按顺序推进 confirmed shadow 并移除 pending。
- 收到他人 op 时先更新 confirmed shadow，再在主线程应用到文档，并重放仍有效的 pending 投影。
- 任一批次被拒时，它及依赖它的后续批次全部进入恢复副本，客户端重新取快照并重建投影，禁止在错误 shadow 上继续发送。

### 5.4 批次原子性
- 一次 commit 产出的所有 op 打成**一个批次**,共享批次号,打包压缩发送(不逐条发)。
- 服务器对批次**原子处理**:批内任何一行未通过校验(涉及他人持锁的行;或锁关闭模式下版本落后)→ **整批拒绝回弹**,客户端提示原因(如"第 N 行正被 X 编辑")。不存在半批生效。
- 拒绝发生时客户端恢复服务器确认态，并把拒绝前的完整核心 ASS 自动保存为带时间戳的恢复 `.ass`，不得静默丢弃脚本或批量操作结果。

### 5.5 脚本兼容性原则
- 同步引擎**不关心改动如何产生**:宏/脚本(TPP、卡拉OK模板机等)整体执行完落一次 commit,钩子对结果与影子做 diff 即可。**任何脚本天然可同步,无需逐脚本适配。**
- 整卷级脚本(TPP、模板机)会触碰几乎所有行,而每个在线成员的焦点都天然持有一行锁,故此类脚本**应在维护模式(§6.4)下运行**,否则大概率被整批拒绝。
- 卡拉OK模板机"删全部旧特效行 + 生成全部新行"导致的 ID 全换在语义上是正确的(生成行无需延续身份),靠日志压缩与快照消化,不做特殊处理。

### 5.6 处理顺序(硬性规定)
宏/脚本执行期间远端 op 在网络线程排队。宏结束落 commit 后,主线程处理顺序**必须**为:
1. ID 对账 pass(§7)
2. 对影子算 diff、发出批次
3. 之后才应用排队中的远端 op

顺序颠倒会导致他人改动被误发为本地改动。

## 6. 并发控制:行级锁(焦点即锁)

### 6.1 锁的获取与持有
- **活动行即锁**:成员焦点落在某行 → 客户端自动向服务器申请该行锁,同时释放上一行的锁。
- 锁授予前(申请在途的短暂窗口),该行编辑暂缓(悲观等待);正常网络下延迟不可感知。
- 申请被拒(他人持锁)→ 该行进入只读态,显示"X 正在编辑"。
- **新插入的行天然属于插入者**,无需预先申请锁。

### 6.2 锁的执行:双层,服务器为准
- **体验层(客户端 UI)**:被他人锁定的行,编辑框与网格编辑只读 + 锁定标识。**选中/浏览永不被阻止**,只挡编辑。
- **正确性层(服务器,强制)**:服务器维护每房间锁表,**对每一个到达的 op 做锁校验——任何 op 涉及他人持锁的行,整批拒绝**。脚本、批量操作、粘贴等一切绕过编辑框的路径都由这一层兜住。UI 只读仅是体验,不承担正确性。

### 6.3 锁的释放
- 焦点切走立即释放；连接断开或 30 秒未收到连接心跳也立即回收。
- 连接心跳与锁租约分离：焦点行 60 秒无编辑或交互时释放硬锁，但保留 presence。用户恢复编辑前必须重新获锁，授予前控件保持只读。

### 6.4 维护模式(硬冻结)
- 用于整卷批处理(TPP、卡拉OK模板机等)。申请后:**服务器暂停房间内其他成员的写权限(全员只读并显示横幅),申请者获得全文件独占写**;跑完手动释放(或断线/超时自动释放)。
- 之所以必须是硬冻结:行级锁下每个在线成员的焦点都占着一行,整卷脚本几乎必然撞锁,软提示无法解决。
- 房内任何成员均可申请，先到先得。10 分钟无本地批次自动释放，单次最长 60 分钟。
- 非持有者可发起取消请求；持有者可立即同意，30 秒无响应后请求者可强制取消。强制取消写入审计日志，持有者随后提交的批次会被拒并进入恢复副本。

### 6.5 锁开关(房间级策略)
- 开关为**房间级策略,建房时设定,服务器强制执行,全房统一**。默认开启，建房后不可变。
- **禁止实现为客户端本地开关**(各端行为不一致会直接破坏数据一致性)。
- **锁关闭时的回退行为**:保留软占用高亮(presence,"X 正在此行"警告,不拦截)+ **版本校验**:op 的 base_version 落后于服务器当前版本 → 拒绝该批次并提示"该行刚被 X 更新",客户端刷新该行,由用户决定是否重做。**不静默覆盖、不自动合并。**

### 6.6 已知取舍(明确接受)
- 锁开启时,"时轴与翻译同时修改同一行"不再支持,改为串行等待;因锁随焦点切换即时释放,实际等待通常为秒级,可接受。

### 6.7 批注旁路
- 校对可对某行挂**批注/修改建议**，内容为留言加可选建议字幕文本。批注以行 collab_id 为锚，创建不受行锁限制。
- 批注记录创建时行版本以及 open/accepted/rejected/resolved 状态，不做讨论串和整行字段建议。删除行的批注随墓碑保留。
- 采纳建议必须先取得该行锁并校验创建时版本，在同一原子操作中修改 Text 与批注状态；拒绝/解决只改批注状态。离线时批注只读。

### 6.8 Undo 与锁
- Aegisub 原生 undo 是全文件快照，不能通过“远端不建撤销点”实现协作隔离；协作模式必须改用**本成员已确认批次的逆 op 栈**。
- Ctrl+Z/Ctrl+Y 只撤销/重做本成员已确认批次，逆 op 仍经过行锁和 base version 校验。目标行后来被修改、锁定或删除时安全拒绝，不覆盖他人；离线单机继续使用原生 undo。

## 7. ID 卫生:commit 钩子内的对账 pass

每次本地 commit、**算影子 diff 之前**,对全文档跑一遍 ID 清洗(纯遍历,毫秒级)。需覆盖的脏场景:复制粘贴、Duplicate Lines、切分行、合并行、脚本 copy 行再插入、新建行、删除后撤销复活、跨项目粘贴外来 ID。

四条规则,按序执行:
1. **无 ID 的行 → 铸新号**(diff 中自然成为 insert)。
2. **同一 ID 出现多次 → 只留一份,其余重铸。** 保留判定:以影子中该 ID 对应行为参照,位置键与内容最接近的保留原 ID,其余视为新行。(切分行场景下自然表现为:前半保留身份,后半为新行。)
3. **ID 命中本地"墓碑缓存"(最近被删过)又出现 → 发 `restore` 而非 `insert`。** 客户端影子中保留最近删除行的缓存用于识别"撤销删除复活",不需要 hook undo 本身。
4. **本房间从未见过的外来 ID → 客户端保留不动,由服务器最终校验**:服务器收到 insert 时查全房历史(含墓碑),ID 冲突则服务器侧重铸,并将"旧 ID → 新 ID"映射回传客户端更新 extradata。

原则:**客户端清洗 + 服务器兜底,双保险。房间之间 ID 空间相互独立。**

## 8. 房间与鉴权

### 8.0 成员与文档初始化
- v1 不做账号系统。入房时填写房内唯一昵称，服务器分配 session/member ID；短暂断线可用重连 token 恢复同一会话。
- 创建房间以当前打开文件的核心 ASS 作为初始快照，创建前先执行 ID 对账。
- 加入已有房间前必须先保存、放弃或取消当前未保存改动；成功后只在内存加载服务器快照，不自动写入本地字幕文件。

### 8.1 两级密码
- **服务器访问密码**(后端可选开启):入口门禁。开启后,握手第一步必须校验;失败或超时 → 直接断开,**不返回任何服务器信息**。
- **房间密码**:保护具体项目内容。凭 **房间名 + 房间密码** 进入房间。
- **房间名本身是共享秘密的一部分**:**不提供任何"列出服务器上所有房间"的接口**。入房是"名字 + 密码"双盲。

### 8.2 握手次序(硬性规定)
1. 客户端连接 → 若服务器启用了访问密码,第一条消息必须是服务器密码校验;失败/超时 → 断开,零信息返回。
2. 通过后,客户端发"加入房间"(房名 + 房密)。
3. **"房间不存在"与"房间密码错误"必须返回同一个错误**(统一为"房间名或密码错误"),防止靠报错差异枚举房名。
4. 全部通过 → 入房,推送全量快照 + 当前序号,开始增量同步。

### 8.3 房间生命周期
- **建房策略:任何通过服务器密码校验的人均可创建新房间**(房名未被占用即可,创建时设定房密与锁策略开关)。
- 建房竞态:房名唯一约束,服务器原子地"占名或拒绝"。
- **房间持久化,空房不销毁**。服务端可配置 N 天无活动冷归档，`0` 表示关闭且为默认值。
- 冷归档生成压缩快照、裁剪已包含的 op 日志并从热索引卸载；原房名和密码再次入房时自动恢复，绝不按天数永久删除字幕。

### 8.4 安全要求
- 服务器密码与房间密码**一律使用 Argon2id**（16-byte salt、64 MiB、3 iterations、parallelism 2），禁止明文落盘。
- 客户端同时支持 `wss://` 与 `ws://`。公网部署强烈建议在 Go 服务前使用 **Caddy 反向代理**终止 TLS，并通过 `wss://` 连接。`ws://` 会明文传输服务器密码、房间密码、字幕和协作数据，只允许用于本机、隔离开发环境或可信局域网，不得直接暴露到公网；客户端首次连接每个 `ws://` 地址时必须提示风险。
- 所有连接的第一条应用消息都是访问认证；未配置访问密码时接受空值。5 秒未认证或认证失败直接断开，不返回应用元数据。
- "加入房间"与服务器密码校验接口按 IP 限流：5 分钟 10 次失败后封禁 15 分钟。仅信任配置的反向代理网段传来的真实 IP。
- 客户端密码默认只驻留内存；Windows 上勾选“记住”后写入 Credential Manager，普通配置和日志禁止出现密码。

## 9. 服务器实现

- 语言:**Go**,单二进制,部署于普通 VPS。
- 协议:**WebSocket + JSON**。消息类型:op 批次 / ack / 批次拒绝(带原因与行号)/ 锁申请与授予/拒绝 / 锁释放 / presence / 心跳 / 全量快照 / 入房与鉴权 / 维护模式申请/授予/释放 / 批注。
- 状态**按房间分片**(房间 ID 为 key),每房间一份:核心 ASS 权威文档、Styles/Script Info 版本、**锁表**、presence 表、带 revision 的 op 日志、墓碑表、批注和房间策略。每房间由单 goroutine 串行定序，广播只发同房间连接。
- 持久化:**append-only op 日志 + 定期快照**,重启可恢复;存储用 **SQLite**。
- 服务器职责:定序、**锁仲裁与逐 op 锁校验**、维护模式仲裁、批次原子处理、(锁关闭模式)版本校验、ID 最终校验与重铸、鉴权与限流。
- SQLite 使用 WAL；接受批次时在同一事务写权威状态、op 日志、墓碑和审计记录。每 500 批或 5 分钟生成快照，日志不足以补齐客户端 revision 时改发全量快照。
- 提供本机 CLI：`serve`、`hash-password`、`backup`、`rooms stats/archive/unarchive`；HTTP 仅额外提供不含版本和房间信息的 `/healthz`，不做 Web 管理后台。

## 10. 客户端(Aegisub fork)实现 — C++ 集成三件套

1. **Commit 钩子**:挂在 Aegisub 内部提交/通知机制上;本地每次 commit 触发「ID 对账 → 影子 diff → 发批次」。commit 类型(文本/时间变更)可用于缩小 diff 范围。另需挂**活动行变更事件**用于锁的申请与释放。
2. **线程模型(硬性纪律)**:后台 WebSocket 线程只负责收发;收到的 op 入线程安全队列,post 自定义 wx 事件唤醒主线程;**所有对字幕数据与 UI 的修改只在主线程执行**(wxWidgets 非线程安全)。发送方向同理:主线程入发送队列,后台线程冲刷。
3. **协作 Undo**:进入协作会话后停用原生全文件快照 undo，维护本成员已确认批次及其逆 op。远端应用标记为不广播，仍通知 UI 刷新；离开协作会话后恢复原生 undo。

客户端同步状态固定为 `confirmed shadow + pending batches + projected shadow`。文本框逐键 commit 不等待网络；发送顺序由单一队列保证。前序批次拒绝时，其后依赖批次一并保存恢复副本并重取快照。

Windows 网络层使用 WinHTTP WebSocket；`wss://` 使用 TLS 与系统证书库，`ws://` 使用不加密 HTTP。后台线程只收发与解析，主线程通过 wx 事件应用。Linux/macOS 编译时关闭协作模块。

UI 增量:
- 网格行的锁定标识(占用者名字)+ 被他人锁定行的只读态;连接状态指示。
- 连接对话框:服务器地址 + (可选)服务器密码 + 房名 + 房密。四项配齐才进入协作模式。建房界面含锁策略开关。
- 批次被拒 / 版本落后的提示(toast 级,非模态)。
- 维护模式的申请入口与全员横幅。
- 断线重连对账的逐行二选对话框(保留服务器版 / 用我的覆盖)。

断线后允许继续编辑，并把断线基线、当前核心 ASS 与待处理批次持久化到用户数据目录。重连时对 base/local/server 做三方比较：单边变化自动采用，双边变化按行或 Styles/Script Info 节二选；完成后短暂取得维护模式，原子提交 resolved delta 并立即释放。

## 13. 已确定的 v1 范围边界

- 锁策略建房后不可变；默认开启。
- 不合并额外 `lua_api` 扩展。
- 冷归档天数由服务端配置，默认 `0` 关闭；归档可自动恢复且不永久删除。
- 批注是留言加可选建议文本，不做讨论串或整行字段补丁。
- 不做 Web 管理后台，使用本机 CLI 与 `/healthz`。
- 房内任何成员均可申请维护模式，并遵循超时与取消请求规则。
- 不做账号系统、CRDT/OT、字段级实时合并、视频/附件同步、行内共同编辑。

## 14. 协议与资源限制

- WebSocket 路径为 `/v1/ws`。所有消息含 `protocol_version`、`type`、`request_id`、`room_revision` 与 payload。
- 控制消息使用文本 JSON；序列化后超过 32 KiB 的批次/快照使用 zlib 压缩二进制 JSON。单条消息解压后上限 64 MiB。
- 房名做 Unicode NFC 规范化、大小写敏感、长度 1–64 字符；昵称 1–32 字符且房内唯一；房间密码 8–128 字节。
- 非法消息、未知必需类型、revision 缺口和超限解压均必须安全失败；`wss://` 的 TLS 证书错误同样必须失败且不可绕过，不得尝试猜测或静默兼容。
